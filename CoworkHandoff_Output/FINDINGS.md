## 1. Compile-risk scan (removed / renamed members)

Searched every other C# script in `Assets` for references to the members removed or
renamed in the rewrite:

- MechController: `dashSpeed`, `momentumDrag`, `landingRecoveryTime`, `dashInitialSpeed`,
  `dashSustainSpeed`, `dashSettleTime`, `airMomentumDrag`, `airControl`,
  `ascendAcceleration`, `minLandingLag`, `maxLandingLag`, `dashHopVelocity`
- MechCombat: `punch1Knockdown`..`punch4Knockdown`, `launchForwardSpeed`,
  `launchUpSpeed`, `comboResetTime`
- MechHealth: `launchGravity`, `launchDrag`, `maxLaunchTime`

**Result: NO references found in any other script.** BoostManager, CameraPivot,
CostManager, LockOnUI, MechShooter and TargetManager are clean. The project should
compile with the new scripts installed.

Notes:

- `SimpleMechAI` (one of the five new files) still declares its **own** fields named
  `dashSpeed` and `landingRecoveryTime`. These are the AI's private copies, not
  references to MechController, so they are safe — just don't confuse them in the
  Inspector.
- `MeleeHitbox` (new) declares its own `launchForwardSpeed` / `launchUpSpeed` — again
  its own serialized fields, intentional (per-hitbox launch used when a mid-string hit
  fills the knockdown bar).
- `TutorialInfo` scripts and the Cinemachine sample scripts are stock Unity content and
  do not reference any Mech classes (not hand-audited line by line).
- Renamed serialized fields mean **the scene's old tuned values are silently dropped**
  (Unity can't migrate values across a rename) — the new defaults apply. That is not a
  compile error, but it is why MORNING_CHECKLIST.md asks you to re-verify the Inspector.

## 2. Animator / animation asset audit (read-only)

This was not explicitly in the task list, but it changes the morning checklist a lot,
so it's reported here. Only ONE animator controller exists in Assets:
`Assets/Animation/Player.controller`. Findings:

1. **No `Melee4 -> Melee1` (i.e. punch4 -> punch1) transition exists yet.** The 8-hit
   loop cannot happen until you add it. (Checklist item 1.)
2. **The controller has NO `HitDown`, `Recover`, or `Die` trigger parameters and no
   knockdown / lie-down / get-up / death states.** The new `MechHealth` calls
   `SetTrigger("HitDown")`, `SetTrigger("Recover")` and `SetTrigger("Die")` — these will
   log "Parameter does not exist" warnings and the mech will physically fly and land
   (code-driven) but **visually never play a lie-down animation**. The Animation folder
   contains no knockdown/death clips at all (only punch1-4, gethit, idle, run, float,
   hard landing), so clips must be sourced (e.g. Mixamo) as well. This looks like the
   single biggest missing piece for the knockdown feature to read on screen.
3. **No punch clip has an `EndAttack` animation event.** Present events: punch1
   (EnableRightFist, DisableRightFist, SwitchToPunch1Camera), punch2 (Enable/DisableLeftFist),
   punch3 (Enable/DisableRightFist), punch4 (EnableLeftFoot, DisableLeftFoot,
   SwitchToPunch4Camera, SwitchToNormalCamera). Without `EndAttack`, every swing ends
   only via the 2.5 s `comboSafetyTimeout` failsafe — combos will feel extremely
   sluggish until the events are added. (Checklist item 2.)
4. **Melee state names are `punch1..punch4`, not `Melee1..Melee4`.** The new
   `MechCombat.MeleeLungeRoutine` waits for a state literally named "Melee1" before
   freezing the windup pose; since the state is named "punch1" it always falls back to
   the 0.3 s timeout. Works, but the freeze timing is approximate. Optional fix:
   rename state `punch1` to `Melee1` (state names are not animation clip names — safe),
   or leave it and accept the fallback.
5. **`Running(Faster) -> punch1` requires BOTH `Melee1` AND `DoStep`.** Conditions on a
   single transition are ANDed. `DoStep` is consumed when entering the step, so a
   step-cancel melee will usually fail this transition and the step animation plays out
   frozen instead. Fix (checklist): remove the `DoStep` condition so the transition is
   `Melee1` only. There is no Any State -> punch1 transition.
6. **punch4's clip fires `SwitchToPunch4Camera` on EVERY playthrough** — including hit 4
   of an 8-hit string (mid-combo), not just the true finisher. The code path
   (`RegisterHit`) already switches cameras only on the correct hits; the clip events
   duplicate this unconditionally. Suggest deleting the three camera events
   (SwitchToPunch1Camera / SwitchToPunch4Camera / SwitchToNormalCamera) from the clips
   and letting the code drive cameras. Same for punch1's `SwitchToPunch1Camera`.
7. Both mechs appear to share `Player.controller` (no second controller found anywhere
   in Assets). All checklist animator work therefore happens in one place — but see
   QUESTIONS.md.

## 3. Review of untouched scripts

### BoostManager.cs — OK
Simple and sound. Overheat clears only at full recharge (correct EXVS behavior — the
new landing-lag code depends on `isOverheated`, which works as expected). No issues.

### CameraPivot.cs — 2 notes
- **No vertical tracking**: `directionToEnemy.y = 0` means an enemy launched into the
  air (the new finisher!) or rising on boost leaves the frame vertically. The camera
  pivot also snaps to `player.position` with no height smoothing, so the player's dash
  hop/skim adds slight vertical jitter to the camera. This is the main motivation for
  the drafted `LockOnBattleCamera.cs` (see Drafts/).
- If the enemy dies and is destroyed/disabled the null check handles it, but the camera
  simply freezes its last rotation — acceptable for now.

### CostManager.cs — 2 notes
- Cost pools are 6000 with `unitCost` 2000, but **there is no respawn system** — after
  one death the match can't continue, and the win log only appears after three deaths
  of the same side. Either wire a respawn (ROADMAP) or set `maxTeamCost` equal to one
  unit cost for now so a single kill ends the match.
- `CheckWinCondition` only logs to console; no game-over state/UI exists (ROADMAP item).
- Not `DontDestroyOnLoad` — fine for the single-scene project.

### LockOnUI.cs — 1 real null-ref risk, 1 mismatch
- **Null-reference risk**: the early-out `if (enemyTarget == null || playerCombat == null
  || lockOnImage == null) { lockOnImage.enabled = false; ... }` dereferences
  `lockOnImage` inside the branch that runs when `lockOnImage` may be null. If the
  Image reference is ever unassigned, this throws every frame. (Report only — left
  as-is per permissions.)
- **Range-check mismatch**: LockOnUI measures red-lock distance with `y` flattened
  (horizontal only), while the new `MechCombat.GetDistanceToTarget()` uses full 3D
  distance. With big height differences the ring can show red while MechCombat treats
  the target as out of red lock (or vice versa). Cosmetic, but worth aligning later.
- `Camera.main` is cached in Start — fine since the Cinemachine Brain lives on the one
  main camera.

### MechShooter.cs — works with the new scripts, 3 notes
- No compile issues with the new systems; `FireWeapon()` is still called by the new
  MechCombat only when the target is not yellow-locked. It remains aim-pose only (no
  projectile) — that's what Drafts/MechShooterV2.cs addresses.
- **Not disabled while downed/dead**: `MechHealth.SetControlScripts` disables
  MechController / MechCombat / SimpleMechAI but not MechShooter, so a queued
  `shootTimer` keeps bending the spine/arm bones during the knockdown animation for up
  to 0.5 s. Minor visual glitch; becomes more visible once real projectiles exist.
- Shooting is possible mid-melee (MechCombat blocks inputs only during Landing /
  Staggered / end lag), which raises the aim pose while punching. Harmless today;
  MechShooterV2's cooldown/ammo makes it easier to gate later.

### TargetManager.cs — 1 real bug, 1 note
- **Behind-camera bug**: `lockOnReticle.transform.position =
  Camera.main.WorldToScreenPoint(...)` has no `z > 0` check (LockOnUI does this
  correctly). When the target is behind the camera the reticle appears mirrored on
  screen. Report only.
- `Camera.main` is called every frame (uncached) — trivial cost at this scale, but
  cache it when you next touch the file.

### Cross-cutting observations (report only)
- **Dead duplicate health fields**: `MechController` and `SimpleMechAI` both declare
  `maxHealth` / `currentHealth` / `isDead` that nothing reads or writes meaningfully —
  `MechHealth` is the real authority. Consider deleting these fields later to avoid
  tuning the wrong number in the Inspector (they're serialized and look important).
- `MechController.TakeHit` default stagger is 0.8 s vs `MeleeHitbox.hitStunDuration`
  0.9 s — the hitbox passes its own value, so the default is only a fallback. Fine.
- `MeleeHitbox.hitStunDuration` (0.9 s) comfortably covers the AI's 0.5 s chain gap and
  the player's buffered chains — victims stay locked during strings, as intended.
